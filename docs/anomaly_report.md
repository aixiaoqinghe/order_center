## 二、逐条详解
### 异常1：并发超卖
- **现象**: Day5 订单 CRUD 无并发保护。Day6写压测脚本模拟200 并发下单同一商品，验证无锁时会超卖(成功数 > 库存 或 库存负数)
- **原因**: 库存检查(SELECT)和扣减(UPDATE)不是原子操作，并发下多个请求都读到"库存够"，都执行扣减，导致超卖。
- **处理**: 加 Redis 分布式锁。lock.py 的 acquire 用 SET NX PX 抢锁，release 用 Lua 脚本原子 "比对+删除"。创建订单时按product_id升序加锁，临界区内完成"查库存 + 校验 + 锁定库存 + 写订单"，finally逆序释放。
- **处理是否彻底**: 超卖解决了，但引入异常2、3
- **遗留**: 锁冲突不重试 -> 成功数低于库存，真实项目可加等待/重试

### 异常2：锁冲突不重试
- **现象**: 200并发下单时，抢不到 Redis 锁的请求直接失败，返回 HTTP 400。成功下单数低于库存数(比如库存100，只成功60，另外40因抢不到锁被拒)。
- **原因**: acquire 抢不到锁返回 None, order_service 抛 LockAcquireFailedError，全局异常处理器转400。没有等待/重试机制。
- **处理**: Day6 选择的策略是"抢不到就拒绝"，没做重试。
- **处理是否彻底**: 否
- **遗留**: 加锁重试 -> 留后续优化。

### 异常3：连接池打崩
- **现象**: 200并发压测下单接口时，接口大面积报错，报 QueuePool limit of size 10 overflow 20 reached 或连接超时。
- **原因**: database.py 里 pool_size=10, max_overflow=20, 最多30个连接。200并发远超30，大量请求排队等连接，等超时报错。更深层: Day6接口用同步 DB (SessionLocal) 跑在 async def 里，同步 DB 调用阻塞事件循环，一个请求卡住会拖累其他请求。
- **处理**: Day6 没处理。压测暴露了这个矛盾，但当时优先跑通功能。
- **处理是否彻底**: 没解决。这是架构层面的矛盾(同步DB + 异步外壳)，不是调大连接池能根治的。
- **遗留**: 留 Day13 端到端时优化。可选方案：换异步 DB 驱动 (asyncpg + SQLAlchemy async)、或把同步 DB 操作丢线程池 (run_in_executor)、或调大连接池(治标不治本)。

### 异常4：重复消费
- **现象**: Day7 写 mq_dup_test.py, 用 publish_order_created 发两条order_id=627 的相同消息，验证消费者会不会重复扣库存。
- **原因**: MQ 不保证"不重投"————网络抖动、 ACK 丢失、生产者重发，都会导致同一条消息被消费多次。没有幂等 -> 库存重复扣。
- **处理**: 两层幂等。
    1. Redis setnx idem:order:{order_id}, TTL 2h。抢到继续，抢不到 return (快速拦截，不可靠)。
    2. DB 唯一约束 consumer_idempotent.order_id 主键。插入时 IntegrityError -> catch 后跳过插入，直接往下扣库存(可靠兜底)。
- **处理是否彻底**: 防住了"完全重复"。但防不住"处理中崩溃"的半成品(见异常8)，Day9 补第三层状态判断。
- **遗留**: 第三层 -> Day9已做(异常8).

### 异常5：死信处理
- **现象**: Day8 模拟消息消费失败，验证死信机制
- **原因**: 消息消费可能失败————业务失败(库存不够、订单不存在)或临时故障(网络、死锁)。失败不能无限重试，要有个"兜底"。
- **处理**: 分类处理。
    - 业务失败 (ConsumeStockError) -> 直接进死信(重试无用)
    - 临时故障 (其他 Exception) -> 重试，x-retry-count header 计数，超3次进死信
    - 进死信: 发 order.dlx.queue + 写 dlx_msg 表 (两者都做)
    - 重试用延迟队列 order.retry.queue (TTL 5s, 过期回 order.create)
- **处理是否彻底**: 机制完整。但 order.dlx.queue 没消费者，消息堆着没人看 -> Day9 补死信消费者 (异常11).
- **遗留**: 临时故障重试未实测 (异常6).

### 异常6：临时故障重试未实测
- **现象**: 重试逻辑( x-retry-count 、延迟队列、3次超限进死信) 代码写完，但没有真正端到端跑过一次。
- **原因**: 临时故障 (网络抖动、死锁、DB瞬时不可用)难复现，不像业务失败可以故意造。
- **处理**: 逻辑已写，未实测。
- **处理是否彻底**: 不确定。逻辑看着对，但没验证过。
- **遗留**: Day13 端到端时想办法模拟(比如临时关 DB 制造故障)，或接受"逻辑写了但未测"。

### 异常7：幂等第三层
- **现象**: Day8 做幂等，只是做了两层: Redis setnx + DB 唯一约束
- **原因**: 前两层只防"完全重复"，防不住"处理中崩溃": 插了 consumer_idempotent(status=0) -> 扣库存到一半 -> 进程崩 -> 消息没 ACK -> MQ 重发。重发时 Redis key 还在(setnx失败) -> 第一层拦住 -> 直接 return -> 库存只扣了一半，永远不对。
- **处理**: Day9 加第三层: 查 consumer_idempotent, 按 consume_status 分支
    - status = 1 -> 已成功，return
    - status = 0/2 -> 半成品/失败，继续处理(不return)
    - 位置: setnx 之后、DB插入之前
    - 查到 0/2 继续后，走到插入必然主键冲突，catch后跳过插入，直接扣库存
- **处理是否彻底**: 缓解了，没根治。因为扣库存 SQL (total -= n) 不幂等，重发时会把没扣完的再扣一遍(如果上次扣了一半)。真正根治要"扣库存可重入"(记录每条消息扣了哪些)
- **遗留**: 扣库存不幂等，留后续。

### 异常8：status=0残留
- **现象**: Day8 插 consumer_idempotent 时，status先写0("处理中")，处理成功后才改1。如果处理中途崩了(没走到改1)，这条记录停在 status = 0，不知道是处理中还是崩了。
- **原因**: 下次消息重发，看到 status = 0，不知道该不该重处理。
- **处理**: Day9 第三层看到 status=0 -> 判定"上次没处理完" -> 继续处理(重新扣库存)，处理成功 -> 改 status = 1, 所以 status = 0 不再"卡死"，会被重新处理。判定依据是 status=0/2 都重处理，status=1 直接 return。
- **处理是否彻底**: 同异常7————扣库存不幂等，重处理会重复扣。
- **遗留**:同异常7。

### 异常9：629-632 四条消息没扣库存
- **现象**: Day7 用 mq_dup_test.py 发了几条测试消息(order_id 629/630/631/632 等)，这些消息被当时"任务2 版本的消费者"消费掉了。那个版本的消费者还没实现扣库存逻辑，所以消息消费了，库存没扣。这四条订单的库存和实际不符。
- **原因**: 测试过程中换过消费者版本，旧版本只做了幂等，没做扣库存，把测试消息"消费掉"了，但没产生扣减。
- **处理**: Day7-8 没处理，识别为"测试数据污染"。
- **处理是否彻底**: 未解决。是数据问题，不是逻辑bug。
- **遗留**: 留 Day13 处理。修法: 手动补扣这四条订单的库存，或直接删掉这四条测试订单。

### 异常10：dlx_msg.msg_id 不优雅
- **现象**: dlx_msg.msg_id 是 bigint 主键，Day8 用 uuid 取模生成。
- **原因**: 想 Python 侧生成 id，不等 DB 自增。uuid 取模能塞进 bigint，但不优雅。
- **处理**: Day8 没改。
- **处理是否彻底**: 不算bug(碰撞概率极低)，但设计不干净。
- **遗留**: 留 Day13。可改成: 用 uuid 前8字节、或改主键类型、或直接用自增。

### 异常11：order.dlx.queue 没消费者
- **现象**: Day8 死信机制做完后，order.dlx.queue没有消费者。死信消息发出去，就一直堆着、没人看、没人处理。
- **原因**: Day8的优先级是先跑通"死信能进去"，消费者留给后面。当时的取舍是"消息先堆着，人工去管理界面看"。
- **处理**: Day9补了 scripts/consumer_dlx.py: 消费 order.dlx.queue, 从消息体拿 order_id, 查 dlx_msg 拿 nack_reason/nack_type/msg_id。日志warning + 控制台输出 + 追加写 logs/dlx_alerts.log。标记 dlx_msg.msg_status = 1。ACK。 catch 所有异常，只记日志，不抛(死信消费者绝不能失败)。
- **处理是否彻底**: 基本解决。但告警是占位(日志 + 文件)，不是真发钉钉/邮件；写文件是同步IO，死信爆发时会阻塞。
- **遗留**: 告警占位、同步写文件阻塞，见异常16。

### 异常12：同步 DB + 异步外壳矛盾
- **现象**: Day6 压测暴露。接口 async def，但 DB 用同步 SQLAlchemy Session，200并发打崩连接池。
- **原因**: 异步框架里跑同步DB调用，会阻塞事件循环，并发能力差。这是架构层面的矛盾，不是调大连接池能根治的。
- **处理**: Day6 没处理，优先跑通功能。
- **处理是否彻底**: 没解决。
- **遗留**: 留 Day13。可选方案:
    1. 换异步 DB 驱动(asyncpg + SQLAlchemy async)————彻底，但要重写 DB 层
    2. 同步 DB 操作丢线程池(run_in_executor)————折中
    3. 调大连接池————治标不治本

### 异常13：超时关单半成品可能重复回滚
- **现象**:  超时关单逻辑是"回滚库存+改订单状态为3"。如果回滚库存成功、改状态前进程崩了，消息没 ACK -> MQ 重发 -> 重发时查订单 status 还是 0 -> 又回滚一次库存。
- **原因**:  回滚库存(total += n, locked -= n) 和改状态不在一个原子操作里。跟异常7/8同一个根问题：扣减/回滚不幂等。
- **处理**: Day9 没处理。靠"状态判断"做幂等(status=0才关)，但防不住"回滚了、状态没改"的半成品。
- **处理是否彻底**:  没根治。跟消费幂等一样，要"回滚可重入"(记录这条订单回滚过没)才能根治。
- **遗留**:  扣减/回滚不幂等，留后续。

### 异常14：publish_order_timeout 失败丢超时计时
- **现象**: 超时消息在 create_order commit 之后发。如果 commit成功、publish_order_timeout 发消息失败(MQ挂了、网络断)，订单创建了，但超时消息没发出去 -> 这个订单永远不会被超时关单，库存永远锁着。
- **原因**: "订单落库"和"发超时消息"是两步，不在一个事务里。MQ 发消息不能跟 DB 事务绑定。
- **处理**: Day9 没处理。
- **处理是否彻底**: 没解决。
- **遗留**: 真实项目用本地消息表(订单落库时同时写一条"待发消息"记录，另一个进程扫描发送)或事务消息保证原子。

### 异常15：超时关单失败进死信未实测
- **现象**: 超时关单失败(ConsumeStockError)会进死信。但这条路径没实测过————因为"回滚失败"不好造(要 locked_stock < n 才触发)。
- **原因**: 故障难复现，跟异常6同类。 
- **处理**: 逻辑写了，未实测。
- **处理是否彻底**: 不确定。

### 异常16：死信消费者同步写文件阻塞
- **现象**: consumer_dlx.py 写 logs/dlx_alerts.log 用的是同步IO( open(..., "a") )。死信不频繁时没事，死信爆发时同步写会阻塞事件循环，拖慢整个消费者。
- **原因**: 异步脚本里跑同步IO，会阻塞事件循环。
- **处理**: Day9 用同步写，简化。死信不频繁，可接受。
- **处理是否彻底**: 没根治。真实项目用异步写(aiofiles) 或丢线程池。
- **遗留**: 留后续。 

### 异常17：死信查不到记录消息丢失
- **现象**:  死信消费者收到消息后，拿 order_id 查 dlx_msg。如果查不到(Day8写表失败、或 order_id 对不上)，日志告警后直接 ACK。结果: 消息从队列删了、表里也没有，这条死信彻底丢失。
- **原因**: 查不到记录时，没有"重试"或"暂存"机制，直接 ACK 了。
- **处理**: Day9 选择"查不到 -> 告警 + ACK" (消息不能一直堆着)。
- **处理是否彻底**: 没解决。丢消息时简化取舍。 
- **遗留**: 真实项目查不到对应"不 ACK, 进另一个兜底队列" 或 "写文件暂存"。留后续。

### 异常18：一条 order_id 多条死信标记漏
- **现象**: 死信消费者标记 msg_status=1 时，SQL 是 WHERE order_id = ? AND msg_status = 0 ORDER BY msg_createtime DESC LIMIT 1, 只标记最新一条。如果同一个 order_id 有多条未处理死信，其他条永远 msg_status=0。
- **原因**: 用 LIMIT 1 简化，假设"一个 order_id 只死一次"。
- **处理**: Day9 用 LIMIT 1。
- **处理是否彻底**: 没解决。场景罕见(一个 order_id 通常死一次)，但存在。
- **遗留**: 留后续。可改成"全部标记"或"按msg_id精确标记"。

## 四、面试可讲的故事（3个）

- **故事1: 并发超卖 -> 分布式锁(异常1+2+3)**

我项目 Day6 专门写压测脚本模拟200并发抢同一个商品库存，先证明无锁会超卖————因为查库存和扣库存不是原子操作。然后加 Redis 分布式锁，用 SET NX PX 抢锁、Lua 脚本释放，按 product_id 升序加锁防死锁，finally 逆序释放。超卖解决了，但压测暴露两个新问题：抢不到锁的请求直接失败，成功数低于库存；200并发把连接池打崩，因为我的 DB 是同步的、跑在 async 接口里，阻塞事件循环。这两个我知道优化方向，当时优先保正确性。

- **故事2: 消息重复消费 -> 两层幂等 + 发现第三层(异常4+7+8)**

MQ 不保证不重投，所以我做了幂等。第一层 Redis setnx 快速拦截，第二层 DB 唯一约束兜底。后来我意识到这两层只防"完全重复"，防不住"处理中崩溃"————如果插入了处理中记录、扣库存到一半进程崩了，消息重发时第一层会拦住，但库存只扣了一半。所以Day9补了第三层:查消费状态，status=1 直接返回，status=0/2 说明是半成品或失败，继续处理。但我也知道这没根治，因为扣库存 SQL 本身不幂等，真正根治要扣减可重入。

- **故事3: 同步DB + 异步框架的架构矛盾(异常3+12)**

我项目用 FastAPI 异步框架，但 DB 用的是同步 SQLAlchemy。Day6 压测200并发时连接池直接打崩，报 QueuePool limit reached。表面是连接池不够，深层是架构矛盾————同步 DB 调用跑在 async 接口里会阻塞事件循环，不是调大连接池能根治的。我知道三个方向: 换异步驱动 asyncpg (彻底但要重写DB层)、把同步操作丢线程池(折中)、调大连接池(治标)。当时优先跑通功能，留到端到端优化。
