# 阶段3 需求文档（requirements.md）

## Q1 定位
电商平台订单系统。用户下单购买商品，系统处理订单、库存、支付（模拟）。

## Q2 业务闭环
用户选购商品 → 下单（锁库存） → 生成订单（待支付） → 用户模拟支付（扣金额） → 订单完成 → 返回模拟物流消息
- 支付失败/超时未支付 → 超时释放库存 → 订单关闭
- 库存策略：下单时预占（锁库存）并发 MQ，消费者异步实际扣减（total_stock 和 locked_stock）；支付时仅改订单状态；超时未支付则回滚库存（total 和 locked 都加回）

## Q3 量级
- 日订单量：约 1 万
- 峰值 QPS：约 140（按大促 2 小时集中估算并放大）
- 明确不做分库分表：单库单表足够支撑该量级，且当前 MySQL 能力待加强，不引入超出能力的复杂度

## Q4 核心功能

| 功能 | 说明 | 为什么是核心 |
|---|---|---|
| 用户注册/登录 | 用户注册账号并登录 | 一切业务的前提 |
| 商品浏览 | 查看商品列表与详情 | 下单的前提 |
| 创建订单 | 用户选商品下单，系统生成订单并锁库存 | 项目主链路 |
| 查询订单 | 查询单个订单与订单列表 | 订单闭环必需 |
| 取消订单 | 用户主动取消未支付订单并释放库存 | 订单闭环必需 |
| 模拟支付 | 用户"支付"（仅改状态，不接真实支付） | 订单状态推进必需 |
| 超时自动关单 | 未支付订单到期自动关闭并释放库存 | 库存回收，防占用 |
| AI 订单咨询 | 用户就自己的订单向 AI 提问 | 差异化亮点 |

## Q5 明确不做
- 真实支付对接：需要企业商户资质，且属于独立子系统；本项目用模拟支付替代
- 真实物流：仅返回模拟物流消息，不对接真实物流系统
- 分库分表：当前量级不需要，且超出当前能力

## Q6 技术亮点
- 主亮点1：分布式锁防超卖 —— 高频并发下单场景下的核心难点
- 主亮点2：MQ 异步解耦 —— 下单与库存扣减解耦，含幂等、死信处理
- 差异化亮点：AI 订单咨询 —— 99% 学生项目没有，展示 AI 集成能力

## Q7 订单超时关单实现方式
选择延迟队列（基于 RabbitMQ 死信队列实现）。
理由：项目已使用 RabbitMQ，用死信队列实现延迟可复用现有组件，不引入新技术栈；相比定时扫表实时性更好，相比 Redis 过期监听更可靠。
