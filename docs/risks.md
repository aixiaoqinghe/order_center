## 风险

### 1.并发超卖
- **风险描述**
  高并发下，同一商品被卖出超过实际库存
- **触发场景**
  100 个用户同时下单同一商品，接口并发执行"查库存→判断够→扣库存"，如果"查"和"扣"之间没有锁保护，多个请求都读到"库存10"，都判断够，最终扣了12次。
- **应对方案**
 - 预防：Redis 分布式锁（key=product_id），同一商品串行处理；DB 层加"条件 UPDATE"（WHERE stock >= n），双保险
 - 兜底：库存对不上（total < 0 或 locked > total）时告警，人工核对
 - 已知缺陷：Redis 锁单点，宕机可能锁失效 → 升级 Redlock（这条写进"已知缺陷"）

### 2.MQ重复消费
- **风险描述**
 订单重复消费,业务重复执行，库存紧张。
- **触发场景**
 1. 消费者处理慢,MQ超时重投
 2. 消费者ACK丢失,订单处理了,但是回到队列等待下次消费
 3. MQ 重启后,订单重复消费
- **应对方案**
 1. DB 唯一约束 + 消费状态判断(`consume_status=1` 已处理则跳过；`order_status=3` 已取消则跳过扣库存。order 状态为 0待支付/1已支付/2已完成/3已取消，没有"已处理"值)
 2. Redis set nx 命令,确保每个订单只能被消费一次,要设置过期时间


### 3.消息丢失
- **风险描述**
 消息丢失,导致订单处理失败
- **触发场景**
 1. 生产者发送的消息,MQ因为网络断开/MQ没持久化等问题,导致消息丢失
 2. MQ存了消息,但是消费者没拿到,MQ重启了
- **应对方案**
 1. 开启生产者Confirm机制，确保生产者发送的消息到了MQ中(核心)
 2. 开启消息持久化 durable = True + delivery_mode = 2(核心)
 3. mandontary = True + Return 确保生产者消息路由到了相应的队列
 4. auto_ack = False 开启手动ack + 死信兜底
 5. 延迟队列设置时间,检查消息是否丢失


### 4.死信堆积
- **风险描述**
 数据不一致,订单处理失败,库存异常
- **触发场景**
 大量消息失败，死信消息失败，死信队列没有处理
- **应对方案**
 把死信堆积监控接入告警系统,阈值设置成30条,超过30条,则告警,人工介入,排查原因,修复问题,批量重放(如业务失败不能直接重放),重新入队处理


### 5.Redis锁失效
- **风险描述**
 锁失效,导致数据不一致,库存异常
- **触发场景**
 1. 业务执行时间 > 锁过期时间
 2. 锁被其他线程误删
 3. Redis宕机
- **应对方案**
 1. 锁的过期时间应设置的比业务执行时间要多,使用看门狗续期机制
 2. Lua 脚本解决防误删
 3. 使用 Redlock 解决单点Redis故障问题


### 6.多商品部分锁成功
- **风险描述**
 库存被白占
- **触发场景**
 下单涉及多个商品，可能“第一个商品锁成功,第二个商品锁失败”
- **应对方案**
 把“锁多个商品库存”这个操作放在同一个 DB 事务里,任意一个商品锁失败了,整个事务回滚,保证事务原子性,已锁的自动撤销
 兜底: 定时对账,检查是否有"订单不存在但库存被锁"的脏数据,人工/自动修复


### 7.AI接口超时
- **风险描述**
 请求超时,用户AI咨询等待时间长,用户体验感不好
- **触发场景**
 1. 大模型API慢,调用超时
 2. 网络慢
- **应对方案**
 1. 降级:返回一个兜底回答(比如"AI助手暂时不可用,您的订单状态是:待支付")
 2. httpx 设 timeout,提示用户稍后重试


### 8.DB连接池耗尽
- **风险描述**
 连接池被占满,新请求无法获取连接,接口大面积超时
- **触发场景**
 1. 慢查询堆积
 2. 连接没释放
 3. 并发太高
- **应对方案**
 1. 增加连接池大小
 2. 优化慢查询
 3. 超时释放连接
 4. 连接池耗尽启动告警 + 限流

### 9.x-retry-count丢失
- **风险描述**
 重试次数丢失,订单一直重试处理,一直不通过,订单积压
- **触发场景**
 1. 代码,忘记更新重试次数
 2. 重试次数没有设置成功
- **应对方案**
 如果 headers 丢了,消费者默认按"第一次"处理(重试次数从0开始) -> 可能无限重试
 更稳妥:用 Redis 或 DB 记录重试次数,不依赖消息 header 重试次数,避免重试次数丢失

### 10.延迟队列消息丢失
- **风险描述**
 延迟队列消息丢失,导致超时关单/延迟重试不触发,订单/消息卡住
- **触发场景**
 延迟队列没有消息持久化
- **应对方案**
 延迟队列开启持久化 durable = True + 消息持久化 delivery_mode = 2 + TTL消息也要持久化

### 11.死信表写不进
- **风险描述**
 死信表写不进,无法人工排查原因,订单处理失败
- **触发场景**
 1. DB 挂了/连接失败
 2. 死信表字段长度不够,插入失败
 3. 死锁,插入失败
- **应对方案**
 1. 死信表插入失败时,降级记日志文件
 2. 告警
 3. DB 恢复后,从日志文件补录


### 12.关单与 MQ 消费者库存回滚竞态
- **风险描述**
 关单先于 MQ 消费者执行时，旧代码会错误地把 total_stock 也加回去（下单只动了 locked_stock，total 从来没被减过），导致库存凭空多出；同时 MQ 消费者因 locked_stock 已被释放，UPDATE 的 `WHERE locked_stock >= n` 不满足 → `rowcount=0` → 抛 `ConsumeStockError` → 调用方直接发死信并 ACK，扣库存不再执行
- **触发场景**
 1. MQ 延迟/积压，超时关单或手动取消先执行（旧代码只锁 inventory 行，没有订单行锁，两个入口可以并发）
 2. 旧关单分支写 `total_stock += n` 且 `locked_stock -= n`，凭空加 total
- **应对方案（现行实现）**
 1. 关单和 MQ 消费者都拿订单行锁 FOR UPDATE，强制串行化，不可能同时跑
 2. 关单用 `consumer_idempotent.consume_status` 判断 MQ 状态（订单级可靠信号，与扣库存在同一事务提交）
 3. MQ 未消费（`consume_status != 1`）→ 只释放 `locked_stock`，不加 `total_stock`（total 从未被减过，不用补）
 4. MQ 已消费（`consume_status = 1`）→ 只补回 `total_stock`（locked 已随扣减清零）
 5. MQ 消费者拿锁后查 `order_status=3`（已关单）则跳过扣库存，置 `consume_status=1` 并 ACK，不再扣库存、不重投
- **状态**
 上述两个问题（关单凭空多 total + MQ 扣不到库存后消息进死信、扣减不再执行）已修复。另有明确保留的边界：`rowcount=0` 时库存没扣但仍置 `consume_status=1`，关单会按「已扣过」只补 total，导致 total 虚增、locked 永久悬空；现已补 `logger.warning` 可观测，但错账仍在（见 README「已知缺陷」）
